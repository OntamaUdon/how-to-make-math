# 第12章 公開の総まとめと、この先へ

ゲームを3本作って、公開しました。**もうあなたは「ゲームを作る人」です。**

この最終章では、公開まわりの知識を一度きちんと整理し、
そのあと「次に何をするか」の地図を渡します。

## 書き出しの仕組みを理解する

なんとなく手順に従ってきたので、何が起きているのかを説明します。

<Statement kind="definition" title="エクスポートで起きていること">

1. あなたが書いたシーン・スクリプト・画像・音が、**`.pck` という1つの箱**にまとめられる。
2. その箱を読んで動かす**エンジン本体**（＝エクスポートテンプレート）が用意される。
3. 両者がセットで出力される。

つまり **「エンジン本体」＋「あなたのデータ」** の2つ組です。
Web書き出しなら `index.wasm`（エンジン）と `index.pck`（データ）に対応します。
</Statement>

これが分かると、いくつかのことが腑に落ちます。

- **なぜテンプレートのダウンロードが要るのか** … エンジン本体はエディタに入っていないから。
- **なぜバージョンを合わせる必要があるのか** … 箱の形式がバージョンで変わるから。
- **なぜ `res://` に書き込めないのか** … 書き出し後は `.pck` の中＝読み取り専用だから。
- **なぜ Web版は初回のロードが長いのか** … 数十MBのエンジン本体を毎回落としているから。

## 置き場所と書き出し先の選び方

| 出したい形 | 書き出し先 | 置き場所の候補 |
| --- | --- | --- |
| ブラウザで遊ばせる | `Web` | itch.io、GitHub Pages、Cloudflare Pages、自分のサーバ |
| Windows で配る | `Windows Desktop` | itch.io、Booth、Steam |
| Mac で配る | `macOS` | itch.io、Steam、App Store |
| Android で配る | `Android` | Google Play、itch.io（apk直配布） |
| iPhone で配る | `iOS` | App Store のみ |

<Statement kind="remark" title="迷ったら Web 一択">
**遊んでもらえる確率が、Web は桁違いに高い**です。
ダウンロードもインストールも要らず、URLをクリックした3秒後に遊び始められる。

個人制作の最初の何本かは、**Web版だけ出す**のが正解です。
「PC版も出したい」は、Web版が遊ばれてから考えれば十分です。
</Statement>

## Web書き出しの完全版チェック

3本作る間に触れた内容を、ここにまとめます。

### 書き出し設定

| 項目 | 設定 |
| --- | --- |
| プリセット | `Web` |
| `Thread Support` | **オフ**（普通のサーバに置けるようになる） |
| エクスポートパス | `build/web/index.html` |
| 「デバッグでエクスポート」 | **オフ**（オンだとファイルが重く、動作も遅い） |
| レンダラー | `Compatibility`（プロジェクト設定側） |

### 動かないときの原因表

<Statement kind="definition" title="Web版トラブル対応表">

| 症状 | 原因と対処 |
| --- | --- |
| **真っ白のまま** | `index.html` を直接開いている。**サーバ経由**で開く（`python -m http.server`） |
| **読み込みが止まる** | ファイルが揃っていない。`.wasm` `.pck` `.js` 全部を同じ場所に置く |
| **itch.io で「入口が見つからない」** | zip の中がフォルダ1段になっている。**中身だけ**を zip にする |
| **`SharedArrayBuffer is not defined`** | `Thread Support` をオンで書き出した。オフで出し直すか、配信側で対応する |
| **音が鳴らない** | ブラウザの規則で、**ユーザーが何か操作するまで音は出ない**。タイトルのボタンを押してから確認する |
| **キー操作が効かない** | ゲーム画面をクリックしてフォーカスを当てる。埋め込みページではよくあること |
| **スマホで操作できない** | キーボード前提の操作になっている。タッチ操作かボタンUIを足す |
| **セーブが消える** | ブラウザのデータ削除。Web版は消える前提で設計する |
| **とにかく重い** | レンダラーを `Compatibility` に。画像を小さく。パーティクルを減らす |

</Statement>

### 読み込みを軽くする

Web版で気にする価値があるのは**初回ロード時間**です。

- **画像を必要以上に大きくしない**（4K の画像を 64px で表示していないか）
- 使っていない素材を削除する（`.pck` に全部入ります）
- BGM は `.ogg`（圧縮が効く）。`.wav` の長い曲は容量を食い潰します
- プロジェクト設定 → `レンダリング → テクスチャ → VRAM Compression` は
  Web では扱いに注意が要るので、まずは触らないでおくのが無難です

## デスクトップ版を出すときの注意

### アイコンを変える

- **Windows**：エクスポート設定の `Application → Icon` に `.ico` ファイルを指定。
  （PNG から `.ico` を作るオンラインツールがいくつもあります）
- **macOS**：`.icns` を指定。
- ゲーム内のウィンドウアイコンは、プロジェクト設定の
  `アプリケーション → 設定 → Icon` で指定します。

### 署名の話

<Statement kind="remark" title="署名がないと警告が出る">
- **Windows**：SmartScreen が「不明な発行元」と警告を出します。
  署名証明書は有料（年間数万円）なので、個人制作では**警告が出る前提**で配ります。
  配布ページに一言書いておくと親切です。
- **macOS**：署名と公証（Notarization）がないと、そのままでは起動できません。
  Apple Developer Program（年額あり）が必要です。
  無料で配る範囲なら、ユーザーに「右クリック → 開く」を案内する方法もあります。

この面倒さも、**まず Web で出す**ことを勧める理由のひとつです。
</Statement>

## スマホ向けに出すには（概要）

Android の要点だけ挙げます。細部はバージョンで変わるので、
やるときは公式ドキュメントの「Exporting for Android」を見てください。

1. **Android SDK と JDK** を入れ、Godot のエディタ設定でパスを通す。
2. **デバッグ用キーストア**を作る（配布用は本番キーストアが別途必要）。
3. `プロジェクト → Android ビルドテンプレートをインストール`。
4. エクスポートで `Android` を追加し、パッケージ名（`com.yourname.gamename`）を設定。
5. **タッチ操作に対応させる**。ここが本題です。

<Statement kind="definition" title="スマホ対応で本当に大変なのは操作">
書き出し自体は設定作業です。難しいのは**操作の作り直し**。

- 画面に**バーチャルパッド**（`TouchScreenButton` や `Button` で自作）を置く
- 画面のどこを触ったかで移動する（`_input` で `InputEventScreenTouch` を拾う）
- 傾け（加速度センサ）で操作する

さらに**画面比率**が機種ごとにバラバラなので、
ストレッチ設定と UI のアンカーがきちんとしていないと崩れます。
第1章でストレッチ設定を最初にやらせたのは、この日のためでもあります。
</Statement>

## Steam で売るには（概要）

- **Steamworks** に登録し、**アプリごとに $100 の登録料**（一定額の売上で返還される制度があります）。
- 審査・ストアページ作成・ビルドのアップロードが必要。
- 実績やクラウドセーブを使うなら **GodotSteam** などのアドオンを導入。
- 個人開発でも十分に出せますが、**1本目に選ぶ場所ではありません。**

**順番としては、itch.io で何本か出して反応を見る → 手応えのある1本を磨いて Steam**、
というのが現実的です。

## 公開前チェックリスト（総合版）

<Statement kind="remark" title="出す前に、これだけは">

**遊べるか**
- [ ] 最初から最後まで通してクリア（またはゲームオーバー）できる
- [ ] リトライ・タイトルに戻るが機能する
- [ ] 出力タブに赤いエラーが出ていない
- [ ] わざと変な操作をしても壊れない

**伝わるか**
- [ ] **操作方法**がタイトル画面か配布ページに書いてある
- [ ] ゲームの目的が最初の10秒で分かる
- [ ] スクリーンショットとサムネイル画像を用意した
- [ ] 説明文が2〜3行ある

**権利は大丈夫か**
- [ ] 使った画像・音・フォントのライセンスを確認した
- [ ] CC BY の素材があれば**作者名を明記**した
- [ ] 他社ゲームからの流用がない
- [ ] ゲーム名が既存の作品と紛らわしくない

**技術面**
- [ ] 別のブラウザで動作確認した
- [ ] ウィンドウサイズを変えても崩れない
- [ ] Web版なら `Thread Support` オフで書き出した
- [ ] バージョン番号を付けた

</Statement>

## 権利まわりの整理

<Statement kind="definition" title="押さえておくべき4点">

**① Godot 自体のライセンス**
Godot は MIT ライセンスで、**ロイヤリティは一切かかりません。**
売上がいくらになっても支払いは不要です。クレジット表記も義務ではありません。
ただし MIT ライセンスの性質上、**著作権表示とライセンス文を同梱するのが正式**です。
公式ドキュメントに「ライセンスの遵守」という項目があるので、
商用で出すときは一度目を通してください。

**② 素材のライセンス**
第5章のとおりです。**CC0 を選ぶのが最も安全**。
CC BY なら作者名を明記。CC BY-NC は有料化できなくなるので注意。

**③ フォント**
埋め込み・再配布が許可されているか確認します。OFL のフォントなら安心です。

**④ 名前と表現**
既存作品と紛らわしい名前は避けます。
実在の人物・企業・商標を扱うときは慎重に。
</Statement>

## 遊んでもらうために

公開しただけでは、まず誰も来ません。これは実力とは関係ない話です。

- **動くGIFを作る**。静止画より圧倒的に伝わります。3〜5秒でいちばん面白い瞬間を。
- **SNSに出す**。`#つくったゲーム` `#indiedev` `#godot` などのタグを添えて。
- **ゲームジャムに出る**。期間内にテーマに沿って作るイベントで、
  itch.io で常時いくつも開催されています。
  **感想がもらえる**のがいちばんの価値です。
- **友達に目の前で遊んでもらう**。これが最強の改善材料です。
  黙って見ているだけで、直すべき点が10個見つかります。

<Statement kind="remark" title="感想が来なくても、それは失敗ではない">
最初のゲームに反応が無いのは普通のことです。
反応の量は、面白さより**露出の量**で決まる部分が大きい。

大事なのは、**「完成させて公開した」経験があなたに残ったこと**です。
これは何本作っても消えません。2本目からは、同じことをもっと速くできます。
</Statement>

## 続けるためのコツ

<Statement kind="definition" title="作りかけで終わらせないための4つ">

**① 作る前に「完成」の定義を書く**
「タイトル → ステージ3つ → クリア画面。これで完成とする」と紙に書く。
書いていないと、永遠に足し続けて終わりません。

**② 最初の1週間で「遊べる」状態にする**
絵も音もなくていい。**四角が動いて当たり判定がある**状態を早く作る。
面白いかどうかは、そこで初めて分かります。

**③ 面白くなかったら、早くやめる**
これは失敗ではなく**判断**です。
四角の状態で面白くないものは、絵を付けても面白くなりません。
早くやめて次に行くほうが、粘って作り込むより結果的に良いものが作れます。

**④ 小さく作って、必ず公開する**
「完成させて公開する」という一連の流れを、何度も通すこと。
1本の大作より、**10本の小品**のほうが確実に上手くなります。
</Statement>

## 次に学ぶこと

この部で扱わなかったもののうち、次にやると効くものを地図にします。

### すぐ効くもの

| テーマ | なぜ効くか |
| --- | --- |
| **`TileMapLayer`** | 地形をタイルで描ける。ブロックを並べる作業が一瞬になる。 タイルセット画像を用意し、`TileSet` に物理レイヤーを足せば当たり判定も付く |
| **状態機械（ステートマシン）** | 「待機・走る・跳ぶ・攻撃・被弾」を `match` や別クラスで整理する。 `_physics_process` が100行を超えたら導入の合図 |
| **`ParallaxBackground` / `Parallax2D`** | 背景を多層にして奥行きを出す。見栄えが一段上がる |
| **`Theme` リソース** | UI の見た目をまとめて定義する。ボタン10個の見た目を一括で変えられる |
| **`Resource` を自作する** | 敵のパラメータや武器データを `.tres` ファイルとして持つ。 データとコードが分離して、調整がとても楽になる |

### 少し先

| テーマ | 内容 |
| --- | --- |
| **シェーダ（`CanvasItem` シェーダ）** | 点滅・輪郭・水面・画面全体のエフェクト。少し書くだけで見た目が化ける |
| **3D** | `Node3D` `CharacterBody3D`。考え方は2Dと同じ。座標が1つ増えるだけ |
| **マルチプレイ** | Godot は高レベルAPIを内蔵。まずはローカル2人プレイから |
| **C#** | .NET版で使える。大規模化するときや、既にC#を書ける人に |
| **AssetLib とアドオン** | Dialogic（会話）、Phantom Camera（カメラ）など、便利な拡張が多数 |

### 情報源

- **公式ドキュメント**（docs.godotengine.org）… 日本語版もあります。
  **クラスリファレンス**（各ノードの全プロパティ一覧）が最強の資料です。
  エディタ内でも、クラス名を `Ctrl+クリック` すると開けます。
- **公式デモプロジェクト**（GitHub の godotengine/godot-demo-projects）…
  動くお手本が大量にあります。**読むより、いじって壊すのが早い**です。
- **コミュニティ**（Godot Forum、Reddit の r/godot、各種 Discord）…
  詰まったときは、エラーメッセージと該当コードを添えて聞けば答えが返ってきます。

## おわりに

この部の最初に、こう書きました。

> **ゲームを作りたいと思ったことがある人はたくさんいます。**
> **でも実際に作り始めた人は、その中のほんの一部です。**

あなたはもう、その「ほんの一部」の側にいます。
しかも作り始めただけでなく、**3本完成させて、公開まで終えました。**
これは、作りたいと言っている人の大多数がたどり着かない場所です。

ここから先は、教材の外の話になります。
作りたいものを作って、詰まって、調べて、直して、また公開する。
その繰り返しの中でしか手に入らないものが、たくさん待っています。

最後に、いちばん役に立つ助言をひとつだけ。

> **次のゲームを、今日始めてください。**

上手くなってから作るのではなく、作りながら上手くなります。
1本目より2本目、2本目より3本目のほうが、必ず速く、必ず良くなります。
あなたはもうそれを3回体験したはずです。

よいゲーム作りを。
