# 第3章 PRとレビューの流れ

## 「Claude が直したけど、本当に取り込んでいいの？」

Claude が作業を終えました。変更は作業ブランチに載っています。
でも、まだ main には入っていません。**ここから先が、人間の仕事**です。

何が変わったのか。意図どおりか。余計な所を触っていないか。
それを確認して、問題なければ取り込む。この手順を支える道具が <Term>Pull Request</Term>（略して PR）です。

## Pull Request：取り込みの申請書

名前が分かりにくいので、言い換えます。

<Statement kind="definition" title="Pull Request">
「この作業ブランチの変更を、main に取り込んでください」という**申請**。
申請書には、変更の説明と、変わった行の一覧（差分）が付く。承認（マージ）されるまで、main は変わらない。
</Statement>

会社の稟議書に似ています。担当者（Claude）が書き、決裁者（あなた）が判断する。
このたとえの限界は、「決裁者が一人でも成立する」ところです。あなたがひとりで運営するサイトでも、PR を通すことには意味があります。**自分の目で見る関門**ができるからです。

## 全体の流れ

5つの段階を、順に進めてみてください。とくに、**どの段階で main が変わるか**に注目です。

<PrFlow />

気づいたでしょうか。main が変わるのは、最後の「マージ」の1回だけです。
それまでの4段階は、すべて「作業ブランチの上」で起きています。だから、途中でやめても本体は無傷です。

> **ここまでのまとめ**：PR を作ることと、main に取り込むことは別。取り込むのは、人が押すボタン。

## 差分（diff）の読み方

PR の中心は<Term>差分</Term>です。GitHub の「Files changed」タブで見られます。

読み方は単純です。

- **緑の行（＋）**：追加された行
- **赤の行（−）**：削除された行
- 変更された行は、赤（前）と緑（後）が並ぶ

たとえば、ある説明文の1行を直す変更なら、こう表示されます（例示用の文です）。

```diff
- ゲームエンジンとは、ゲームを作る道具箱のことです。
+ ゲームエンジンとは、ゲームに共通して必要な機能をまとめた土台のことです。
```

この表示のよい所は、**変わっていない所は見なくてよい**ことです。
500行のファイルでも、変わった3行だけを読めば、何が起きたか分かります。

## レビューで見るべきこと：考え方

では、差分を前にして、何を疑えばよいのでしょうか。
慣れた人が頭の中でやっている問いを、順に書きます。

**1. 頼んだことと、変更が一致しているか**
「第3章の誤字を直して」と頼んだのに、第5章が変わっていないか。**頼んでいないファイルが混ざっていたら、まず疑う**。これがいちばん効きます。

**2. 「消した行」に注目する**
追加より、削除のほうが危険です。意図せず消えた説明や、数式の閉じ括弧がないか。赤い行を先に読むのがコツです。

**3. 数学の内容が正しいか**
このサイトでは特に重要です。定理の主張、証明の論理、記号の向き。Claude の文章は読みやすいぶん、誤りに気づきにくい。**自分で確認できない部分は、取り込まない**という選択もあります。

**4. ビルドが通るか**
`.mdx` の書き方を1つ間違えるだけで、サイト全体のビルドが止まることがあります。PR に自動チェック（CI）が設定されていれば、その結果を見ます。設定されていないなら、手元で `npm run build` を試すのが確実です。

## 直してほしい所があったら

差分の行にコメントを付けられます。「ここは、たとえ話を残してください」のように書きます。
Claude に頼めば、そのコメントを読んで作業ブランチに追加のコミットをします。PR は**自動で更新**されます。作り直しは要りません。

この「差分を見る → コメント → 直る → また見る」を繰り返す作業が<Term>レビュー</Term>です。

## マージと、そのあと

納得したら、「Merge pull request」を押します。作業ブランチの変更が main に入ります。

**マージしたら、すぐサイトが変わるのか**は、別の話です。
公開の仕組み（main が更新されたら自動でビルドして公開する設定があるか）で決まります。これは GitHub ではなく、公開先のサービス側の設定です。

## 取り消したくなったら

マージしたあとで問題に気づいたら、<Term>revert</Term>（打ち消しのコミット）が使えます。
GitHub では、マージ済み PR のページに「Revert」ボタンがあり、**その PR の変更を打ち消す PR** を作れます。履歴は消えず、「戻した」という記録が残ります。

**セーブポイントがあるから戻れる**。第1章のコミットの話が、ここで効いてきます。

## ありがちな勘違い

**勘違い1：「PR を作ったから、もう反映された」**
反映されていません。マージするまで main は同じです。

**勘違い2：「チェックが緑なら、中身も正しい」**
緑は「ビルドが通った・テストが通った」だけです。数学の内容や、意図とのずれは、検査してくれません。

**勘違い3：「全部読まないと、PR を扱えない」**
変更が小さい PR を、**こまめに**出してもらうのがコツです。「1つの PR で、1つのこと」を頼めば、読む量が減ります。

**勘違い4：「マージしたら、もう戻せない」**
戻せます。ただし revert も、新しい変更の一種です。確認せずに押さないでください。

## この部のまとめ

- **GitHub**は、あなたと Claude の共通の机。リポジトリ＝履歴つきのフォルダ。
- **Claude** は、クラウド上で作業ブランチに変更を載せる、手の速い共同執筆者。
- **Pull Request** は、取り込みの申請書。差分を読み、意図・削除・内容・ビルドを疑ってから、人がマージする。

これで、「アップロードしたら何ができるのか」の地図は一通りそろいました。
次の一歩は、小さな頼みごとを1つ、Claude にしてみること。たとえば「この部の第1章の誤字を探して」。PR が届いたら、この章の手順で見てみてください。
