# 第1章 GitHubの基本

## 「最終版_本当の最終版_修正2.docx」問題

レポートを書いていて、こんなファイル名の列を作ったことはありませんか。

- `レポート.docx`
- `レポート_最終.docx`
- `レポート_最終_本当の最終.docx`
- `レポート_最終_本当の最終_先生の指摘反映.docx`

なぜこうなるかというと、**「前の状態に戻れる安心」と「いまの最新版が1つに決まっている安心」を、同時に欲しい**からです。
上書きすると前に戻れない。かといって全部残すと、どれが最新か分からない。

Git は、この板挟みを解くための仕組みです。そして GitHub は、その Git で管理したものを**インターネット上に置いておく場所**です。

## リポジトリ：履歴ごと持ち歩くフォルダ

<Term>リポジトリ</Term>とは、「フォルダ＋そのフォルダの変更履歴」を丸ごと入れた箱のことです。
見た目はふつうのフォルダですが、中に `.git` という隠しフォルダがあり、そこに全部の履歴が入っています。

あなたの `how-to-make-math` フォルダも、実はもともとリポジトリでした。
最初に `git init` を打ったとき、`Reinitialized existing Git repository` と出ましたね。「すでにリポジトリだったので、初期化し直しました」という意味です。

## コミット：ゲームのセーブポイント

履歴は、<Term>コミット</Term>という単位で積み重なっていきます。

<Statement kind="definition" title="コミット">
ある時点のフォルダ全体の状態を、メッセージ付きで記録したセーブポイント。
あとから「この時点の状態」に戻したり、「前のコミットと何が違うか」を見たりできる。
</Statement>

ゲームで、ボス戦の前にセーブしますよね。負けたらそこからやり直せる。コミットも同じです。
このサイトの履歴を見ると、たとえば「Godot入門（全12章）を隠し部として追加」というコミットがあります。**何をしたかの一言**が、セーブデータの名前になっているわけです。

ただし、このたとえには限界があります。ゲームのセーブは通常「最新の1つ」に上書きされますが、コミットは**全部が残って連なります**。だから、10個前の状態にも戻れるのです。

## ブランチ：安全に試せるパラレルワールド

ここで困りごとが出ます。大きな変更を試したい。でも失敗したらサイトが壊れる。

<Term>ブランチ</Term>は、その解決策です。いまの状態から**分かれた別の枝**を作り、そこで好きに変更します。
元の枝（ふつう `main` という名前）は一切変わりません。気に入ったら元に合流させ、気に入らなければ枝ごと捨てます。

次の図で、実際に触ってみてください。

<GitTimeline />

試してほしい順序があります。

1. 「作業ブランチを作る」を押す
2. 「ブランチにコミット」を2回押す。**main の丸が増えていない**ことを確認する
3. 「main にコミット」を押す。ブランチを切ったあとも main は独立して進められる
4. 「main に取り込む（マージ）」を押す

> **ここまでのまとめ**：ブランチの上の変更は、<Term>マージ</Term>するまで main に影響しない。
> だから「失敗しても本体は無傷」で試せる。

## push：自分のPCから、GitHubへ送る

ここまでの話は、全部あなたの**PCの中**で起きています。GitHub はまだ登場していません。

GitHub 上のリポジトリを「リモート」、PCの中のものを「ローカル」と呼びます。
`git push` は、ローカルのコミットをリモートに送る操作です。

あなたが実行したこのコマンドを、意味の分かる形に直してみます。

```text
git remote add origin https://github.com/OntamaUdon/how-to-make-math.git
```

「GitHub のこの住所を、`origin` という名前で覚えておいて」。`origin` は、ただのあだ名です。

```text
git push -u origin main
```

「ローカルの `main` ブランチを、`origin` に送って。`-u` は、次からは `git push` だけで通じるように覚えておいて」。

出力の `Writing objects: 100% ... 1.62 MiB` は、履歴ぜんぶ（約1.6MB分）が送られた記録です。
`* [new branch] main -> main` は「GitHub 側にまだ無かった `main` を、新しく作りました」という意味でした。

## GitHub で何が見えるのか

push したあと、ブラウザで `https://github.com/OntamaUdon/how-to-make-math` を開くと、次のものが見えます。

- ファイルの一覧と、各ファイルの中身（**ソースコードや文章のまま**）
- 全コミットの履歴と、各コミットで何が変わったか
- ブランチの一覧

ここで大事な注意があります。

<Statement kind="remark" title="GitHub に見えるのは「ソース」であって「完成したサイト」ではない">
このサイトは Astro というツールで、`.mdx` というソースを HTML に変換（ビルド）して作られます。
GitHub のファイル一覧に出るのは、変換前の `.mdx` や `.astro` のほうです。
「サイトとしての見た目」を見るには、ビルドして公開する仕組みが別に必要です。
</Statement>

## ありがちな勘違い

**勘違い1：「Git と GitHub は同じもの」**
別物です。Git はPCの中で履歴を管理する道具。GitHub は、その履歴を置いて共有するサービスです。Git だけでも使えます。

**勘違い2：「push したらサイトが公開される」**
公開と push は別の話です。push はコードを置く操作で、公開するかどうかは別の設定で決まります。

**勘違い3：「ブランチを作ると、ファイルが倍になる」**
なりません。Git は「何が違うか」だけを持つので、枝を増やしても重くなりません。

**勘違い4：「公開リポジトリでも、URL を知られなければ見られない」**
公開リポジトリは、検索などで見つかり、**誰でも中身を読めます**。パスワードや API キーを入れたファイルは、置く前に必ず除外してください。一度公開すると、あとで消しても履歴に残ります。

## この章のまとめ

- リポジトリ＝フォルダ＋履歴。コミット＝セーブポイント。
- ブランチ＝安全に試せる別の枝。マージするまで本体は変わらない。
- push＝ローカルのコミットを GitHub に送ること。
- GitHub で見えるのはソース。サイトの見た目は、ビルドと公開の仕組み次第。
